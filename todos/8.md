# 8 — Add structured errors and idempotent writes

Priority: P2
Status: Open
Legacy ID: V1-08
Priority assigned during migration on 2026-11-11; adjustable by the user.

## Outcome and implementation context

Under `--json`, return a documented error object with stable machine-readable codes, a human-readable message, and useful retry guidance. Cover argument validation, unknown/ambiguous IDs, missing projects, database contention, import failures, and partial installation failures. Inspect `src/main.rs`, clap parsing in `src/cli.rs`, and dispatch; account for errors occurring before `App` exists. Avoid mixed success/error documents that cannot be parsed.

Add optional idempotency keys to write operations, starting with node/todo creation. Persist the key, normalized request identity, and result atomically with the write. Retrying the same key and payload should return the original result; reusing a key for different content should fail explicitly. Define which commands support keys and how replay appears in the activity log. Do not treat similarity matching as idempotency.

Acceptance: JSON errors parse consistently and retain nonzero exit codes; text-mode errors remain readable; concurrent identical requests create one node; simulated response-loss retries return the original ID; conflicting key reuse creates no extra mutation.

Decision (William, 2026-11-11): In JSON mode, emit structured JSON errors on stderr with a nonzero exit code; successful results go on stdout. Keep the error stream machine-parseable without an extra plain-text error wrapper. Test stdout, stderr, and exit status independently, including errors before dispatch and partial installation failures. Preserve readable text-mode errors.

Decision (William, 2026-11-11): Idempotency keys are database-wide, not scoped to an agent or session. The same key and request returns the original result without repeating the mutation, including across sessions. Reusing a key with different request content reports a conflict without changing stored data. Store the key, normalized request identity, and original result atomically with the successful write. Test retries across sessions, concurrent identical requests, and conflicting key reuse. The JSON-error destination and key-scope questions are settled.
