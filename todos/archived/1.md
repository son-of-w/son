## Result

Cause: two kinds of lock are refused by SQLite at once, without the busy timeout. (1) Switching a new database to WAL mode needs the file to itself, so of many first opens only one succeeded. (2) `BEGIN IMMEDIATE` and `PRAGMA user_version` during WAL setup or recovery can also return "busy" directly. Measured before the fix: 39 failures in 60 runs of `parallel_sessions_do_not_collide`.

Fix (commit 5d04565, then 0.1.2): `db::retry_busy` repeats such a step with a short pause until the wait ends; `db::open` leaves a database that is already in WAL mode alone; migration takes the write lock, then reads the schema version again. The wait is 10 seconds, or `SON_BUSY_MS` milliseconds. When it ends the command fails with "the database is in use by another session" and changes nothing. Other errors are not retried.

Evidence: 0 failures in 60 runs after the fix, and 0 in 25 runs of both parallel tests at 0.1.2. Tests: `parallel_sessions_do_not_collide` (16 first opens, one project), `parallel_writes_to_an_existing_database_keep_every_record`, `a_held_lock_fails_after_a_bounded_wait_and_changes_nothing` (tests/cli.rs), `a_migration_that_fails_leaves_the_database_as_it_was` (src/db.rs).
