## Outcome and implementation context

Add proposed `son backup` and `son doctor` commands. A backup must capture committed SQLite state safely while WAL and concurrent writers are active; do not simply copy the main database file. Define how this relates to the existing logical JSON export, which intentionally excludes the activity log. Support an explicit destination and verify that a produced backup can be opened/restored in isolation.

Doctor should inspect database/schema compatibility, integrity and foreign keys, search-index consistency, and generated integration files. Report healthy/missing/stale/problem states in Markdown and JSON with actionable next steps. Default to diagnostics without modifying data or configuration; any repair should be a distinct explicit operation. Inspect `src/db.rs`, `src/transfer.rs`, `src/setup.rs`, and `src/instructions.rs`.

Acceptance: a backup made during writes restores consistently, including the agreed history/log contents; existing destination files are not silently overwritten; doctor detects deliberately damaged or stale fixtures and returns meaningful status; no network calls or writes to real user configuration occur in tests.

Decision (William, 2026-11-11): `son backup` creates full, consistent SQLite snapshots, including revision history, activity logs, and idempotency records. Keep JSON export as the portable interchange format. Existing JSON export behavior remains compatible; it is not a substitute for a full database backup.

Additional requirement (William, 2026-11-11): `son import` must accept both son SQLite snapshots and son JSON exports. Extend the existing command rather than introducing a separate SQLite-only import command. Validate format, schema/version, and integrity before modifying the destination; preserve source files and avoid partial destination changes on failure. Keep existing JSON import and stdin use compatible. Test both formats, SQLite history/log/idempotency preservation under the agreed import policy, malformed inputs, unsupported versions, and rollback. Inspect `src/transfer.rs`, `src/db.rs`, `src/cli.rs`, and `src/app.rs`; document supported format selection/detection.

Decision (William, 2026-11-11): Backups are explicit-only for v1 through `son backup`. Do not add automatic backups, scheduling, or automatic retention/pruning policies. Other commands must not create backups implicitly. Backup-format and backup-trigger questions are settled.

Decision (William, 2026-11-11): SQLite import is a full restore, not a merge. Require explicit `--replace` for a nonempty destination; without it, fail without changes. Restore snapshot data consistently, including history, activity logs, and idempotency records. JSON import keeps its existing merge behavior. Test absent/empty destinations, rejection of nonempty destinations without `--replace`, full replacement with the flag, and unchanged JSON merge behavior. Define nonempty conservatively to include retained history/log/idempotency data, not merely live nodes. Coordinate restore with concurrent connections/WAL and preserve the destination on failed validation or restore. Do not create an implicit backup; backups remain explicit-only. The backup and import policy questions are settled.

## Result

`son backup <file|folder>` (`src/backup.rs`): `VACUUM INTO` from the open connection, so the copy is one read transaction: consistent with WAL and with concurrent writers. It holds every table: nodes, edges, tags, refs, synonyms, ops, revisions, edge_changes, events, idempotency, and the search index. An existing file is refused and left as it is; a folder gets `son-backup-<UTC time>.db`. After writing, the copy is opened read-only and must pass `PRAGMA integrity_check`, else it is removed and the command fails. No other command makes a backup; there is no schedule and no pruning. The `backup` command's own log entry is written after the copy, so it is not in the copy.

`son import <file> [--replace]`: the format is found from the first 16 bytes (the SQLite header), else it is read as JSON. `-` is JSON from stdin. JSON import is unchanged (merge). A SQLite file is a full restore:
1. Check: opens read-only; has the tables `nodes`, `edges`, `tags`, `synonyms`; schema version from 1 to the current one; `integrity_check` is ok. Any failure is `import_failed` and nothing changes.
2. A private copy of the backup is made in the temp folder and brought to the current schema with the normal migration. The backup file is only read.
3. In one write transaction on the destination: if it is not empty and `--replace` was not given, fail with `not_empty` and change nothing. Else delete every row of every data table, copy every row from the private copy (same ids, same history and log numbers, the same next history number), and rebuild the search index.

"Not empty" means any node, collection, link, history entry, log entry or key. So a database where commands only ran (log entries) also needs `--replace`. Other sessions wait on the transaction and see the old content or the new. No backup is made implicitly. `--replace` with a JSON file is refused.

`son doctor` (`src/doctor.rs`): runs before the database would be opened for writing; opens it read-only; does not create or upgrade it; not logged. Checks: database (file there and readable), schema (current, older = stale, newer = problem), integrity (`integrity_check`), references (`foreign_key_check`), search index (each live node has one index row holding the text the analyzer makes now; no row for a node that is gone), skill file and instruction file for every agent location where son is set up (same as this version writes = healthy; other = stale; a start mark with no end mark = problem), agent setup (missing when no file is found). Statuses: healthy, missing, stale, problem; each fault names its fix. Markdown and JSON. Exit status 1 and error code `problems_found` only for a problem. Repairs are the existing explicit commands: `son reindex`, `son init`, `son import <backup> --replace`.

Tests (tests/cli.rs): `a_backup_made_during_writes_restores_whole` (12 writers during the backup; in the copy every node has its history and its index row; restore keeps history, log and keys; existing file refused; folder destination; no implicit backups), `restoring_a_backup_replaces_only_when_told_to` (empty destination; refusal with nothing changed; log-only database counts as not empty; garbage, foreign, future-schema and damaged files; JSON merge unchanged; full replacement), `doctor_reports_and_changes_nothing` (missing, healthy, stale index, stale files, broken block, older and newer schema, broken reference, damaged file; no change by doctor).

Not covered by a test: restoring a backup of an older schema version (the path uses the normal migration, which has its own tests in src/db.rs).
