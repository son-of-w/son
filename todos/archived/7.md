# 7 — Preserve change history and support undo

Priority: P1
Status: Done (2026-11-11, version 0.1.6; merge undo arrives with #4)
Legacy ID: V1-07
Priority assigned during migration on 2026-11-11; adjustable by the user.

## Outcome and implementation context

Store previous node revisions and add proposed `son history <id>` and `son undo <id>` commands. The existing revision counter and activity log do not retain overwritten content. Define snapshot coverage for body, title, type, status, scope, tags, provenance, and deleted state, and explicitly decide how links and merges participate. Undo should create a new revision so the reversal itself remains auditable, rather than erasing history.

Inspect all mutation paths in `src/store.rs`, `src/app.rs`, and `src/transfer.rs`. Make snapshot creation atomic with its mutation. Protect undo from silently overwriting a concurrent edit. Display history in Markdown and JSON; coordinate with [#4](4.md) merges and [#2](archived/2.md) provenance.

Acceptance: changes can be inspected and restored without losing intervening history; no-op/failed operations do not create misleading revisions; concurrent edits are handled explicitly; old databases migrate safely; the documented backup policy preserves the intended history.

Decision (William, 2026-11-11): Retain revision history indefinitely in v1, with no automatic pruning. Do not discard revisions based on age or revision count. Test that older revisions remain available for inspection and undo. Explicit purge behavior is specified below.

Decision (William, 2026-11-11): Undo covers link changes and merges as well as node edits. Undoing a merge restores the original memories and their links atomically. If subsequent changes make reversal unsafe, report a conflict rather than overwrite newer work; leave all affected state unchanged on conflict. Check all affected nodes and links within the undo transaction, not only the survivor's revision. Test link undo, merge undo, transaction rollback, and conflicts caused by later node or link changes. Undo itself remains an auditable new revision/operation.

Decision (William, 2026-11-11): `son drop --purge` erases the node and its revision history from the active database, leaving existing backups unchanged. Ordinary `drop` remains reversible. Undo requiring purged history must report that restoration is unavailable rather than partially restoring an operation. Account for snapshots retained by merge/link history so they cannot restore the purged node. Test history removal, unavailable undo, and unchanged backup files. This is logical deletion from the active database, not a promise of forensic erasure. The history-retention, undo-coverage, and purge questions are settled; full-backup contents are specified in [#9](9.md).

## Result

Schema version 6: `ops` (one row for each command that changed nodes or links: kind, time, session, author, `undoes`, `undone_by`, `purged`), `revisions` (each changed node before and after, as JSON) and `edge_changes` (each link added or removed, with its creation time). The code is `src/history.rs`. Every mutation path records through `history::Recorder` inside the same write transaction as the change: remember, todo add, edit, verify, drop, restore, todo done, link, unlink, import. A collection that a command has to create is its own operation.

Snapshot coverage: type, title, body, status, collection, tags, evidence category, evidence references, verification (time, by, note) and the dropped state. `rev` and `updated_at` are kept in the snapshot but are not compared.

Commands: `son history <id> [--op <n>] [--limit] [--page]` and `son undo <id> [--op <n>]`, both with `--json`.

Undo rules:
- Without `--op`, undo reverses the newest operation on the node that is not an undo and was not undone, so repeated undo walks back. With `--op`, any operation, an undo included (that is redo).
- All of the operation is reversed (every node and link it changed) in one transaction, or none.
- Conflict check, inside the transaction: each node must hold the same content as the operation left, and each link must be in the state the operation left. If not, the command fails with "was changed after it" and changes nothing. A collection that would end up dropped while it holds live nodes, and a collection name now taken by another, are conflicts too.
- The undo is a new operation (`kind = undo`, `undoes = <n>`) and a new node revision. History is never rewritten or pruned.
- Undoing a creation drops the node (soft).
- An operation that changes nothing (same edit again, same link again, todo already done) records nothing. A failed command rolls back with its record.

Purge: `son drop --purge` deletes the node, its revisions, its link changes, and its mentions in the activity log. An operation that also changed other nodes keeps their rows but is marked `purged`; undo of it fails with "restoration is unavailable" and changes nothing. Files made before the purge are not touched.

Migration: older databases get empty history tables; the first change to a node records its earlier state.

Merges ([#4](4.md)) use the same recorder, so a merge is one operation over the survivor, the source and the moved links, and undo restores all of it or reports a conflict.

Backup policy: the JSON export does not carry history; the full backup of [#9](9.md) does.

Tests (tests/cli.rs): `history_keeps_every_change_and_undo_walks_back`, `undo_reports_a_conflict_and_changes_nothing`, `undo_covers_links_drops_moves_and_verification`, `old_revisions_stay_and_purge_erases_history`, `an_import_is_one_change_that_can_be_undone`.
