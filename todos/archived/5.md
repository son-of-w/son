# 5 — Support stable scopes outside repositories

Priority: P2
Status: Done (2026-11-11, version 0.1.5)
Legacy ID: V1-05
Priority assigned during migration on 2026-11-11; adjustable by the user.

## Outcome and implementation context

Use collections for noncoding uses such as personal, household, or travel memory, as well as coding projects. An agent must be able to select a stable scope without relying on its current directory. Preserve automatic repository detection for coding agents, but rename the public collection-selection/filter flag from `--project` to `--collection` on every applicable command. Separate where a memory belongs from whether it is reusable elsewhere; do not repurpose the future sync `visibility` field without an agreed design.

Inspect `src/project.rs`, project nodes in `src/store.rs`, all CLI project filters, recall ranking, context, reports, and transfer. Specify explicit selection/default precedence, migration of existing projects, and labels in output. Avoid creating a second disconnected store.

Acceptance: a noncoding agent can create and recall household memory from unrelated directories; coding commands use `--collection` consistently while repository detection remains intact; `son collections` lists collections and `son projects` is rejected; scope identity survives export/import; cross-scope recall and priority follow the agreed policy. CLI output, help, JSON output, errors, and documentation consistently call memory groupings collections.

Decision (William, revised 2026-11-11): Use **collections** as the public term, covering both coding projects and noncoding memory. Rename `--project` to **`--collection`** across remember, recall, edit, todo add/list, context, export, list, and log, and rename **`son projects` to `son collections`**. V1 has not been released, so do not retain compatibility aliases for the old command or flag names. Use collection terminology throughout CLI output and docs: headings, labels, type names, help, validation/errors, pagination suggestions, JSON field names, README examples, generated agent instructions, and tests. This includes `--cross-collection` for the proposed merge opt-in. Test the new command/flags and rejection of the old names, plus consistent human-readable and JSON output. Preserve repository detection and existing stored data through any necessary migration/import translation; storage internals need not be renamed merely to match public wording. References to actual coding projects or project-local agent installation may still use "project" where they do not mean a memory collection.

Decision (William, 2026-11-11): Recall searches all collections by default, including personal and household collections. Matches from the current collection come first; an explicit collection filter narrows results. Use `--collection` for explicit filtering; the legacy `--project` flag is replaced. Test cross-collection results, current-collection priority, and explicit filtering.

Decision (William, 2026-11-11): Collections are organizational only in v1, with no collection-level access restrictions. Any agent using the database can retrieve any collection. Filters narrow searches and do not grant or deny access. Do not introduce collection permissions or describe collections as security boundaries. The terminology, recall-default, and access-policy questions are settled.

## Result

Public names: `--collection` on remember, recall, edit, todo add, todo list, context, export, list and log; `son collections`; the node type `collection` (`son remember collection "<name>"`). `son projects`, `--project` and the type `project` are rejected. Output, help, errors and JSON say collection: `collection`, `collection_id`, `current_collection`, `merged_collections`, `by_collection`, `collections`.

Which collection a command works in, first match wins: `--collection`; the `SON_COLLECTION` environment variable; a `.son-collection` file in the directory or a parent; the git remote's repo name; the git root's directory name; the directory's name. An older `.son-project` file is still read (data, not a command or flag name).

Storage: schema version 5 renames the node type `project` to `collection`. Ids, names and members do not change. The column `nodes.project_id` and the column `events.project` keep their names (internal). JSON export is version 2; a version 1 file (type `project`, fields `project_id` and `project`) is still imported and translated. Collection ids survive export and import.

Recall and access are as decided: every collection is searched, the current one first, `--collection` narrows; collections are not access boundaries and `visibility` is not used for this.

Install scope still says "project" (`son init --scope project`), because there it means a project folder, not a memory collection.

Tests: `a_collection_can_be_chosen_without_a_repository`, `an_export_from_before_collections_is_still_read`, `a_marker_file_names_the_collection` (tests/cli.rs); the migration test in src/db.rs.
