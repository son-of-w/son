## Outcome and implementation context

Add a proposed `son remember --check` path that returns likely existing matches before a write, using local deterministic matching. Define its write behavior clearly so scripts cannot mistake a preview for a saved node. Add a proposed `son merge` command with explicit source and survivor IDs. Similar wording is only a candidate signal, not permission to merge. Preserve useful body content, tags, links, and provenance; keep an audit trail and a way to trace the old IDs.

Inspect `src/analyze.rs`, `src/search.rs`, `src/store.rs`, `src/transfer.rs`, and CLI dispatch. Merge atomically, handle duplicate/self edges and supersession relationships, and coordinate reversibility with [#7](archived/7.md). Explain match reasons and support JSON. Update generated instructions to use the agreed workflow.

Acceptance: checking leaves the store unchanged under preview semantics; meaningful duplicates are surfaced without merging distinct decisions; merge does not lose references or evidence; failed merges roll back; retries do not duplicate links; deleted and cross-project nodes have explicit handling.

Decision (William, 2026-11-11): `son remember --check` is strictly read-only, including when no duplicates are found. It only reports candidate matches; saving, editing, and merging require separate explicit operations. Do not create a project/node, update metadata/indexes, or write an activity event for this preview. Ensure the check path does not create or migrate a database as a side effect; an absent store should yield an empty preview without creating it. Test both matching and no-match cases for absence of persistent changes.

Decision (William, terminology revised 2026-11-11): Allow cross-collection merges only with an explicit `--cross-collection` flag (replacing the earlier proposed `--cross-project` name under [#5](archived/5.md)). Keep the chosen survivor's collection and preserve provenance and links from both memories. Without the flag, reject a merge across collections without partially changing either memory. Test rejection without the flag, successful opt-in, survivor collection retention, and preservation of provenance and links.

Decision (William, 2026-11-11): When memory bodies conflict, require the caller (agent or user) to supply the resolved body explicitly. Do not automatically select or concatenate conflicting content. Preserve both original memories in history, coordinating with [#7](archived/7.md); capture the originals and apply the merge atomically. Reject an unresolved conflict without partial changes. Tests must show that the caller's resolved text is saved and both originals remain inspectable in history. The duplicate-preview, cross-project merge, and conflicting-body questions are settled.

## Result

`--check` on `son remember` and `son todo add`. It is handled before the database is opened for writing: the database is opened read-only with no migration, no activity event is written, and with no database the answer is an empty preview. The output starts with "NOT SAVED"; JSON has `"check": true`, `"saved": false`, no `id`, and `candidates` with `score` and `reasons`. If the database is of an older schema, the check fails and says to run `son init --db-only` (a read-only command does not upgrade).

Matching (`search::duplicates`, `search::likeness`): candidates come from the search index by the title's words; likeness is the share of title words in common (after stemming and stop words), raised when one title holds all words of the other, when the bodies share most words, or when title or body are equal; lowered for a different type. Candidates at 0.5 or more are listed, five at most, every collection searched. It is deterministic and local.

`son merge <source> <survivor> [--body] [--title] [--cross-collection]`:
- Refused, with nothing changed: the same node twice; a collection; a dropped node; a node already merged; different types; different collections without `--cross-collection`; different non-empty bodies without `--body`.
- The survivor keeps its id, title (or `--title`), collection and verification; gets the union of tags and evidence references; takes the source's evidence category only when its own is unknown. With one body empty or both equal, no `--body` is needed.
- Every link of the source moves to the survivor. A link the survivor already has is not added twice; a link between the two is removed.
- The source is dropped and `merged_into` (schema version 7) holds the survivor's id. `son show <source>` prints "MERGED into"; `son show <survivor>` prints "merged from"; JSON has `merged_into` and `merged_from`.
- One operation in the history covers both nodes and every moved link, so both originals stay inspectable and `son undo` restores both nodes and all links, or reports a conflict and changes nothing. The survivor is always part of the record, even when its content does not change.

Generated instructions describe the workflow: check first, then edit, link, or save; merge only stored nodes that say the same thing.

Tests (tests/cli.rs): `check_lists_possible_duplicates_and_changes_nothing` (database file compared byte for byte), `merge_keeps_evidence_and_links_and_can_be_undone`.
