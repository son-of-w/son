# 2 — Add provenance and explicit verification metadata

Priority: P1
Status: Done (2026-11-11, version 0.1.4)
Legacy ID: V1-02
Priority assigned during migration on 2026-11-11; adjustable by the user.

## Outcome and implementation context

Allow optional references to evidence such as a file, URL, conversation identifier, or user statement. Distinguish user-stated decisions/facts from agent observations and agent inferences. Preserve existing `source` (session), `author`, and `origin` semantics; do not overload those fields with evidence links. Add explicit verification metadata such as `verified_at`, separate from `updated_at`. Store references without fetching URLs or reading referenced files automatically.

Inspect `src/db.rs`, `src/store.rs`, `src/cli.rs`, `src/app.rs`, `src/render.rs`, and `src/transfer.rs`. Expose metadata in create/edit/show and JSON; show enough in recall/context to assess trust without flooding output. Old nodes must remain usable with unknown provenance and no implied verification.

Acceptance: migration preserves old data; provenance and verification round-trip through backup export/import; an edit alone never marks a node verified; user statements and agent inferences remain distinguishable. Attribution must describe recorded evidence, not claim automatic truth verification.

Decision (William, 2026-11-11): Use three evidence categories: **user statement**, **observation**, and **inference**. Existing memories remain **unknown** unless explicitly classified. Categories describe how knowledge was learned, not guaranteed accuracy; do not infer a category during migration.

Decision (William, 2026-11-11): Agents may mark a memory verified when they check supporting evidence and record what they checked. Explicit user confirmation is not required. Merely recalling or repeating a memory does not count as verification. Verification must be an explicit operation backed by recorded evidence, not an automatic consequence of saving or editing a node. The evidence-category and verification-authority questions are settled.

## Result

Schema version 4: `nodes.evidence` (`user_statement`, `observation`, `inference`, or NULL for unknown), `nodes.verified_at`, `verified_by`, `verified_note`, and the table `refs(node_id, kind, value, created_at)`. `source`, `author` and `origin` are unchanged. Reference kinds: `file`, `url`, `conversation`, `user`, `other`; a bare web address is a `url`. Nothing is fetched or opened.

Commands: `--evidence` and `--ref` on `remember`, `todo add` and `edit`; `--unref` on `edit`; `son verify <id> --checked "<text>" [--ref]` and `son verify <id> --clear`. `verify` sets `verified_at`, `verified_by` (the session name, else the author) and `verified_note`; it does not change `updated_at`. `edit` never changes the verification fields.

Output: `show` prints "evidence: <category> · verified <date> by <who>" (or "unknown", "not verified"), the check note, and an Evidence list. `recall` and `context` print the category and "verified <date>" only when known. JSON carries `evidence`, `verified_at`, `verified_by`, `verified_note` and `refs` on every node.

Import policy: the fields travel in the JSON export. When the stored content is as new or newer than the file's, a newer verification and new references are still taken from the file.

Tests: `provenance_is_recorded_and_verification_is_explicit` (tests/cli.rs); the migration test in src/db.rs checks an old node stays unknown and unverified.
